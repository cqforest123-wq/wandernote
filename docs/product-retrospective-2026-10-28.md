# WanderNote 产品与工程复盘

日期：2026-10-28（Asia/Singapore）

## 结论

WanderNote 已有可继续打磨的本地旅行日记基础，但不能把“代码已写、单元测试通过、拍过一张界面”合并成“功能全部完成、可放心发布”。目前最需要的不是增加功能数量，而是闭合已有流程、明确数据风险、建立同一提交的构建和验收证据。

建议定位：**无需账号的私人旅行日记，记录每天的文字、照片、清单和花费，Apple Watch 提供旅途速览。**

这是一项待真实用户验证的产品假设，不是已经成立的竞争优势。没有最新 App Store Connect 曝光、产品页浏览、首次下载和转化数据，本次不能解释下载少的原因，也不能给出增长或收入预测。

## 一、回溯：发生过什么

1. 早期以在线 AI、账号/云端和付费入口为主要依赖，审核暴露 AI 故障缺少可用降级。随后加入本地故事 fallback，最终当前运行链改为本地模板，不再调用在线 AI。
2. Watch 从快照协议、原生发送接收、缓存和状态映射逐步发展到定位、步数、日照与停车，工程结构已有相对清晰的边界。
3. 曾混入骑行/运动能力，之后按旅行产品定位清理。相关删除有提交记录；这提醒我们，跨项目开发需要把产品边界写入每次任务的验收条件。
4. 产品收敛为免费、无账号、本机记录、不设套餐数量限制。减少了后端维护面，但数据归档和换机问题没有因此消失。
5. 后续按“多做几个/10 个功能”推进了搜索、筛选、复制、收藏、排序、分享与费用账本。它们改善已有体验，但其中很多只是同一能力的操作，不能当作多个独立卖点。
6. `2026-10-27` 路线图已经写了“先发布硬化，不继续堆外围功能”，之后又新增两批。这反映的是执行顺序偏离了已有判断，不是缺一份更长的功能清单。

## 三、按优先级列出的问题

### P1：照片滤镜保存没有应用滤镜

证据：`screens/PhotoFilterScreen.js:69` 创建空的 `actions`；`73` 行用它重新编码原图；选中的 `filter` 没有传入任何像素处理。预览的颜色覆盖层只存在于 React Native 视图，不会进入保存图片。所谓黑白预览也只是覆盖/压暗，不是真正灰度转换。

影响：用户选择滤镜、看到预览并获得“保存成功”，相册中的输出却没有相应效果，属于可见功能的承诺与结果不一致。

建议：发布前必须二选一，真正实现并验证预览/导出一致，或隐藏这条不完整入口。不要仅修改成功提示来掩盖。

### P1：地图“打开旅程”导航接不通

证据：`screens/MapScreen.js:253` 调用 `navigate('TripDetail')`。`App.js:161` 的地图分支只注册 `Map`，而 `TripDetail` 仅存在于首页分支。用 Babel 解析当前导航声明确认：

```text
home: Home, TripDetail, DayDetail, TripMemo, TripBudget
map: Map
memo: Memo
ai: AI
profile: Profile, YearReport, PhotoFilter
```

影响：从地图直接进入旅程的新增工作流不能正常完成。年度报告的旅程跳转也有相同结构问题，但它目前被入口开关隐藏。

建议：以最小范围调整共享详情路由，并实际测试“地图 -> 旅程 -> 每日记录/清单/花费 -> 返回”，不只修第一层跳转。

### P1：公共 Nominatim 用法与服务政策冲突

证据：`screens/HomeScreen.js:296` 在输入变化后延迟 450ms 调用 `searchPlaces`；`lib/placeSearch.js:43` 指向公共 `nominatim.openstreetmap.org`。`App.js:94` 另有并发重试未解析旅程坐标的 `Promise.all`，没有共享限流。

官方政策明确禁止客户端自动补全，并规定整个应用合计最多每秒一次请求。当前实现不能因为用户少就视作符合政策。

建议：先停止公共端点上的自动补全，审查搜索/地理编码所有调用与缓存、限流、署名、服务可替换性，再决定合规方案。无自建后端不等于必须使用这一公共服务；最终替代方案需要单独验证，不能暗中增加云端。

来源：[Nominatim Usage Policy](https://operations.osmfoundation.org/policies/nominatim/)。

### P1：发布证据没有跟上当前代码

最新 Watch 测试清单记录：安装 `2077def` 后观察过海拔标签和 stale UI；后续 `3d497b7` 的更新安装因 tunnel 超时未完成。历史用户反馈中部分同步与停车通过，但不能据此确认最新版所有流程通过。

前一轮费用截图使用实际 React Native 页面和示例数据，适合检查样式；临时预览入口绕过了正常导航，且使用无操作的保存回调，因此不能作为增删改持久化验收证据。该预览代码已经移除。截图中的开发警告也使它不适合作为正式商店素材。

发布文档明确旧归档早于后续代码，不能直接上传旧包。当前又多了两批本地提交，必须从最终同一提交重新构建和验收。

### P2：花费边界输入可保存零金额

证据：`lib/tripExpenses.js:18` 先验证正数，`20` 行才四舍五入。只读执行当前函数，输入 `0.004 USD`，返回 `amount: 0`，与“金额大于零”的规则不一致。

建议：规范金额精度并在规范化后验证；补小数、粘贴输入、超大金额及币种显示测试。当前工具测试通过不覆盖这个反例。

### P2：草稿输出与多语言外壳不一致

证据：`lib/travelStoryFallback.js:60` 和 `111` 生成主体是固定英语；没有语言参数。`AIScreen` 可以显示中文按钮，却生成英语故事和重复的通用每日行程。

建议：明确标为本地提纲；优先完整支持实际服务的核心语言，不以七套按钮翻译推导七种语言的内容体验。这里需要提升的是输出质量，而不是恢复在线 AI。

### P2：媒体删除和数据清除缺少完整生命周期

证据：`DayDetailScreen.js:169`、`201` 以及旅程/日期删除只移除记录引用；没有回收对应的 Documents 媒体。反复增删照片可能保留孤立文件，尤其本地版的存储占用会持续累积。

另一个失败路径：`ProfileScreen.js:98` 先清除数据键，之后清除媒体，最后才清空内存；若媒体清除抛错，界面仍保留原记录，继续编辑可能重新写入它们。这是源码级失败路径分析，本次没有在真机强制文件删除失败。

建议：设计可重试的删除/清理流程和安全回收，不能先删文件再保存引用，也不能清除一半后让界面表现为完全未执行。

## 四、工程与验证评价

做得好的地方：

- 本地运行导入链的测试确实检查了不可达登录、云同步、在线 AI、购买与广告 SDK，不只是隐藏按钮。
- 数据写入串行化、坏 JSON 不自动覆盖、保存失败可重试、媒体从缓存复制进 Documents，都是有价值的基础工程。
- Watch 保持 iPhone 生成快照、Watch 接收/缓存/映射的边界，runtime 长期持有 provider；定位权限请求与 HealthKit 查询已存在正式代码，不能再笼统判断为“provider 完全没启动”。
- 测试包含协议、glance 映射、停车距离和日照计算；这是可继续建设的基础。

不足：

- 当前主要页面是 JavaScript，`tsc --noEmit` 没有启用 `checkJs`，通过不能说明所有 JS 页面都已充分类型检查。
- 本地测试使用模拟存储、纯函数和部分源码静态检查，没有覆盖真实导航、键盘表单、系统权限、分享面板及相册导出。
- 静态审计输出“0 blocker”只反映它写过的规则；本次发现的导航与滤镜缺陷都不在覆盖范围。
- 仓库没有 `.github` CI 工作流。构建可复现性、测试入口和最终发布证据仍依赖手工记录。
- 路线图、发布资料与“已完成功能”口径出现偏差；新增能力后没有同步更严格的退出条件。

## 五、产品与 UI 复盘

### 应保留的核心

主线是“创建旅程 -> 每天留文字/照片 -> 随时找回 -> 整理分享”。清单和花费都是贴近这条主线的工具。Watch 的价值是减少旅途中掏手机的次数，不是复制全部手机功能。

### 不应夸大的地方

- 城市标记地图不等于旅行轨迹。
- 本地提纲不等于目的地知识或智能路线规划。
- 免费、无账号和本机保存是边界和体验选择，不自动构成难以复制的壁垒。
- 花费增删改、搜索、排序是一个模块的组成部分，不是十个独立获客理由。
- 安装/进程启动成功不等于 Watch 的权限、同步和传感器已全部验收。

### UI 优先事项

1. 旅程详情围绕日期记录组织，清单/花费作为相邻工具，避免不断增加独立主导航入口。
2. 费用页首屏目前大部分用于总额和类别分解；金额录入才是常见动作。小屏/键盘/日期选择器打开时要验证可操作性，不能仅看一张长屏截图。
3. 多页仍用低对比灰色、emoji 和文字符号承担交互，卡片与小字号较多。需要在真实尺寸、动态字体与 VoiceOver 下检查，而不是仅靠主观“高级感”。
4. 草稿与照片滤镜不应占据强于“快速记一条/添照片”的位置，尤其在输出尚未完整时。

### 竞品带来的启示

[Tripsy 官方页面](https://tripsy.app/) 已覆盖结构化行程、资料、费用、协作与 Apple Watch。这说明“再补费用、再补 Watch”不能单独作为差异化结论。WanderNote 更值得验证的是：一个不要求登录、少量操作即可保存每天回忆的小工具，是否比全能规划工具更适合特定用户。

本次只核对了官方公开说明，没有对竞品做逐屏真机测评，不据此评价其真实质量或市场表现。

## 六、建议执行顺序

### 下一批：只做可靠性，不增加对外卖点

1. 修好地图/共享详情导航，补覆盖完整往返的 UI 回归。
2. 真正完成滤镜导出，或者移除不完整入口。
3. 修正地点搜索公共 API 用法和调用节奏。
4. 修正费用精度、表单键盘/日期选择器布局与保存失败反馈。
5. 补媒体回收、清除失败和升级保留测试。

退出条件：每个可见主要按钮都有可验证结果；保存后能冷启动读回；失败不误报成功；无网络不妨碍本地记录。

### 随后一批：建立同一提交的发布候选

1. 固定最终提交，从它重建 iPhone 与 Watch，不复用旧 archive。
2. 一次完成配对真机验收：同步、Location/Altitude、Steps、停车、冷启动、离线缓存、重连与 stale。
3. 从正常入口走完“创建旅程 -> 日记/照片 -> 清单/花费 -> 重启回读 -> 分享”，不使用临时页面注入作为验收替代。
4. 从候选构建重新截图；核对图标、隐私、网络说明和 App Store 更新描述，只写实际可用的能力。
5. 在 App Store Connect 核对真实线上版本、待提交状态和可用 build number，再决定上传/提交。本复盘不替代这一步。

### 发布后：从数据决定方向

- 先看曝光、产品页浏览和首次下载的漏斗，不先断言低下载来自功能不足。
- 找少量确实在旅行或刚旅行回来的人完成一次记录任务，观察阻力和是否愿意继续使用。
- 每轮只选一两个问题修正，保留观察周期；旅行是低频场景，不直接套用每天打开的活跃目标。
- 文件归档/手动导入是“长期私人日记”值得优先评估的信任能力，但按此前决定不在当前版本悄悄增加，另立验收任务。
- 不恢复骑行、云账号、付费墙或广告；任何未来商业模式变化都必须单独决策。

## 最终判断

值得完成一个可靠、定位清楚的版本，再验证有没有用户价值；不值得继续用“又增加了十项操作”替代产品进展。接下来的成功标准应当是：**一个真实旅程能顺畅记录、可靠保存、方便回看；手机与手表经过同一版本的验收；商店说的和用户拿到的一致。**

## 后续落实（2026-10-28）

按用户要求删除照片滤镜，而非继续完善它。已修复共享详情路由、费用精度和保存重试、系统地点查询、本地媒体回收与清除失败路径；本地生成草稿和生成式打包模板已接入七种界面语言。33 项本地测试及 Watch 测试通过，完整 iPhone Debug 模拟器构建通过并包含 Watch app，安装启动显示实际引导页。

以上是对原审计的后续修复，不抹除前面的历史发现。原生界面逐页验收、最新配对真机验证、正式归档、托管隐私页发布和审核提交仍不能标为完成。完整范围与验证边界见 `docs/local-first-release.md` 的 2026-10-28 hardening 记录。
